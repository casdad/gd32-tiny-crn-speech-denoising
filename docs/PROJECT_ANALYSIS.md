# 项目源码分析

本分析依据提交材料中的源码、Keil 配置、训练配置和已有实验记录，不把说明性注释当成运行验证。分析没有访问开发板或原始训练数据集。

## 1. 系统分层

### 开发板主程序

`firmware/app/User/main.c` 实现硬件初始化、SAI/TDM 采集、音频解析、LCD 波形、触摸事件、模式切换和停止后的文件降噪。当前存在 RAW、RNN、CRN 三种模式。

`User/gd32h7xx_it.c` 接收 DMA 完成事件并维护音频软件队列；`User/main.h` 定义 480 点帧和 1024 帧队列。队列放在 `0xC0000000` 开始的 SDRAM，按 `1024 × 960 × 4` 计算占用 3,932,160 字节（3.75 MiB）。固定地址队列不能与其他 SDRAM 使用区域重叠，启动时必须先正确初始化 SDRAM 再访问。

`User/sd_wav_recorder.c` 封装 FatFs、WAV 头、缓冲写入及 LCD 截图。默认自动格式化关闭。`User/crn_model.c` 只包装 AI 模型初始化和 `int8[256] -> int8[32]` 推理；FFT、频带转换和重建位于主程序，而不是该包装文件中。

### 模型训练

`training/tinycrn/model.py` 定义卷积、深度卷积、逐点卷积、单层 LSTM 和 Sigmoid 掩蔽头。正式配置共 71,248 个可训练参数。每个窗口包含 8 帧，LSTM 每次从零状态开始，不是跨窗口持续传递状态的流式模型。

`tinycrn/features.py` 使用 Hann 窗、居中 STFT、按幂次分布频带边界的三角滤波器组和 `log1p(10 × band_mag)`。输出 mask 的监督目标为 clean/noisy 频带幅度比，经 `[0,1]` 裁剪。它不是复杂谱直接预测，也不是严格的 Mel/Bark 标准滤波器组。

`tinycrn/dataset.py` 按样本索引和 worker 编号生成随机数，读取两类音频后截段、混噪并选取一个上下文窗口。同一个索引在相同 worker 分配下跨 epoch 会重复同一随机样本；若希望每轮重新采样，需要显式引入 epoch seed。

### 性能测试工程

`firmware/benchmark` 保留独立驱动和工程路径。与主固件相比，关键差异为 `User/main.c`、`User/gd32h7xx_it.c`、串口实现、Keil 工程，以及新增的 `User/perf_meter.c/.h`。

DWT 统计项目包括 DMA ISR、解析与电平、STFT/频带、CRN invoke、mask/ISTFT/OLA、LCD、TF 写入和整帧。`crn_ai_stubs.c` 中的可选 AI 报告计时返回零，不能将其当作真实推理耗时；应使用性能测试工程的 DWT 数据并说明是否包含中断和调度影响。

## 2. 已实现功能与证据边界

| 内容 | 源码可确认内容 | 尚不能据此宣称 |
| --- | --- | --- |
| 音频录制 | RAW 优先保存、STOP 后按模式处理文件 | 无丢帧的任意时长录音 |
| CRN 预览 | 非录音时每 20 帧最多执行一次预览重建 | 每 10 ms 连续完成全链路 |
| AI 模型 | 256 字节输入、32 字节输出及生成参数 | 与原始 PyTorch 严格数值一致 |
| 板端输出 | WAV 文件、LCD 显示；默认关闭 ES8311 输出 | 已实现实时耳返 |
| PC 评估 | 原 CSV 中包含 SNR 与频带误差 | 板端 PESQ / STOI 或泛化性能 |
| 编译 | 提供 Keil 工程和随附源文件 / 库 | 在当前环境重新编译并通过硬件实测 |

## 3. 最重要的技术限制

### 量化参数没有形成可追溯闭环

主固件中 `CRN_INPUT_FEATURE_Q_MUL=24`、输入零点 `-128`、输出缩放 `1/255` 和输出零点 `-128` 来自当前经验映射。`CRN_OLA_GAIN=1.6` 也是当前重建参数，不能当作数学等价保证。

下一步应从实际量化产物取得 scale/zero_point，保存其来源，并对同一特征样本比较 PyTorch、ONNX、转换后模型与 MCU 的输入、mask 和重建音频。未完成这一对齐前，PC 的改善量不能直接外推为板端指标。

### STFT 和上下文边界需要单独核对

PC 使用 `center=True` 的 STFT 和首帧填充；MCU 使用自己的环形历史、FFT、窗函数、OLA 和量化缓存。帧边界、零填充、归一化、首尾样本、上下文初始化都会影响一致性。不要仅凭双方的 FFT 点数相同就判断端到端等价。

### 录音稳定性与实时性是两件事

DMA + SDRAM 队列用于缓冲处理阻塞；队列达到上限仍可能丢帧。STOP 最多补写 50 帧队列，不能保证任何积压都会完整写入。应同时记录实际录音时间、WAV 样本数、队列高水位和丢弃计数，分别验证数据完整性与运算吞吐。

### 数据划分与评估规模

列表生成器按文件随机切分，无法自动保证说话人独立或录音源独立。小规模输入会产生空验证集。`eval.py` 默认只选少量 clean/noise 文件，并用索引绑定人工噪声标签，需要先核对内容；当前 CSV 缺少 STOI/PESQ，不应填成 0 或补写为已验证值。

## 4. 整理时完成的工程修正

- 删除发布副本中的本机数据路径，`training/main.py` 改用项目相对路径。
- 为已有可视化代码补充遗漏的 `matplotlib` 依赖；STOI/PESQ 保留为可选依赖。
- 为 Keil 工程引用但原材料缺失的 `readme.txt` 补充说明文件，不改变固件逻辑。
- 保留模型权重和必要 `.lib`，而不是把所有二进制一律忽略。
- 排除编译输出、用户 IDE 状态、个人路径列表、原始音频和重复实验产物。
- 未更改网络结构、训练损失、主固件或测试固件的算法实现。

## 5. 建议的后续验证顺序

1. 固定数据划分、环境版本与模型 hash，完成 PC 训练 / 推理 / ONNX 回归。
2. 导出准确量化参数，以同一输入验证 PC 与板端 mask。
3. 对齐 STFT / iFFT / OLA，统计首尾误差和稳态音频差异。
4. 在实际开发板验证编译、录音长度、队列丢帧和输出文件。
5. 最后使用 DWT 测量完整链路并判断是否满足 10 ms 调度预算。
